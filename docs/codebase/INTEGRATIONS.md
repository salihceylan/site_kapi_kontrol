### 3) Secrets and Credentials Handling

- Credential sources: backend `.env` (never committed); Flutter `--dart-define=API_BASE_URL`; per-device MQTT credentials issued by the API at device registration and stored in device NVS.
- Hardcoding checks: `lib/config/app_config.dart` holds only the production API URL (no MQTT credentials); the mobile app never receives MQTT credentials; the firmware pins the broker TLS root certificate (`tls_kok_sertifika.h`). CI runs a secret scan (gitleaks).
- Rotation or lifecycle notes: MQTT ACL/password sync is documented in `MQTT_kurulum.txt`; production credential rotation is a pending user decision (`BEKLEYEN_ISLER.md`).

### 4) Reliability and Failure Behavior

- Retry/backoff behavior: `AuthApi` retries one transport failure after 350 ms for idempotent reads only; mutations such as door open are never retried automatically. Firmware reconnects to MQTT with exponential back-off and jitter.
- Timeout policy: Flutter HTTP requests use a 45-second default timeout and 10 seconds for door open; DB pool has connect/statement timeouts (`DB_CONNECT_TIMEOUT_MS`, `DB_STATEMENT_TIMEOUT_MS`); the HTTP server has keep-alive/header/request timeouts.
- Circuit-breaker or fallback behavior: `NetworkService` health-checks the API; door opening falls back from the local network (UDP, challenge-bound HMAC v2) to the cloud; devices keep an offline log and deliver it in batches acknowledged with `logs_ack`.
- Backend startup: API calls `ensureDbSchema()` before listening and shuts down gracefully on SIGTERM/SIGINT.

### 5) Observability for Integrations

- Logging around external calls: request logger with token masking, global error handler with `errorId` (details only in server logs), MQTT bridge and mail errors logged; `/health` reports database and MQTT bridge status without raw error text.
- Metrics/tracing coverage: none (no APM).
- Missing visibility gaps: no APM, SMTP delivery tracking, or MQTT health metrics beyond `/health`.
