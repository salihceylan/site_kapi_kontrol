## Temel kararlar

1. **Erişim yetkisinin tek kaynağı `apartment_memberships` kalır** (kapı yetkisi, uygulama üyeliği). CRM kayıtları bunun üstüne eklenen bir KAYIT katmanıdır: ilişki türü (malik/kiracı…), tarihler, notlar, hesabı olmayan kişiler, araçlar. Mevcut katılım/onay/daire-sakini akışları (join_requests, `PATCH /manager/apartments/:id/resident`, davetler) AYNEN çalışır ve CRM'e yansır.
2. **Kişi bilgisinin tek kaynağı:** hesabı olan kişide ad/telefon/e-posta `users` tablosundan okunur (kopyalanmaz, sapma olmaz). Kişinin KENDİ hesabında (kendi kaydolan / parolayı sahiplenen) CRM'den DEĞİŞTİRİLEMEZ; SİTENİN YÖNETTİĞİ hesapta (yönetimce / toplu yüklemeyle açılmış sakin hesabı, `isSiteManagedAccount`) ad ve telefon CRM'den değişir ve `users`'a yazılır (e-posta giriş adresidir: yalnız dahili hesapta iletişim e-postası düzenlenir, bkz. commit c8a8541). Hesabı olmayan kişide bu alanlar `site_people`'da tutulur ve CRM'den düzenlenir.
3. **Kayıtlar silinmez:** taşınan kişi "pasif/eski sakin" olur ve dairenin geçmişinde kalır. Her değişiklik `audit_log`'a yazılır (F2.11 geçmişi buradan okunur).
4. **Site izolasyonu (KVKK, F2.10):** yönetici yalnız kendi sitesinin kayıtlarını görür; sakin yalnız kendi kayıtlarını; başka sitenin hiçbir bilgisi dönmez. Kurul üyesi (`BOARD_MEMBER`) yalnız OKUR; görevli (`STAFF`) kişi listesini GÖREMEZ (403 `FORBIDDEN_ROLE`).
5. **Modül:** `people` çekirdek modüldür; katalogda `status: available` olur (hep açık, kapatılamaz). `GET /app/my-modules` ve katalog buna göre `enabled: true` döner.
6. **Doğrudan canlı:** şema ekleyicidir, `ensureDbSchema` ile `migrations/03x_*.sql` aynı DDL'dir; mevcut sakinlerin CRM'e aktarımı (backfill) TEK SEFERLİK ve idempotent çalışır (`platform_backfills(code PRIMARY KEY, done_at)` tablosu ile korunur); mevcut hiçbir kapı yetkisi değişmez.

## Veritabanı (migration `031_people_and_apartments.sql`; 030 modül talepleri içindir)

- `site_people(id BIGSERIAL PK, site_code BIGINT NOT NULL REFERENCES sites ON DELETE CASCADE, user_code INTEGER NULL REFERENCES users ON DELETE SET NULL, full_name TEXT, phone TEXT, email TEXT, note TEXT, is_active BOOLEAN NOT NULL DEFAULT TRUE, created_by INTEGER NULL REFERENCES users ON DELETE SET NULL, created_at, updated_at)`. `user_code` doluysa `full_name/phone/email` sütunları BOŞ bırakılır (okuma `users`'tan). Kısmi tekil indeksler: `(site_code, user_code) WHERE user_code IS NOT NULL`; `(site_code, lower(email)) WHERE user_code IS NULL AND email IS NOT NULL AND is_active`. Telefon normalize: `+90` + 10 hane (`+905551234567`).
- `apartment_residencies(id BIGSERIAL PK, site_code BIGINT NOT NULL, apartment_id INTEGER/BIGINT NOT NULL REFERENCES apartments ON DELETE CASCADE, person_id BIGINT NOT NULL REFERENCES site_people ON DELETE CASCADE, relation TEXT NOT NULL DEFAULT 'resident' CHECK (owner|tenant|family_member|resident), is_current BOOLEAN NOT NULL DEFAULT TRUE, move_in_date DATE NULL, move_out_date DATE NULL, created_at, updated_at)`. `resident` = ilişki belirtilmemiş (mevcut sakinler bununla aktarılır; malik/kiracı olduğunu yönetici sonradan işaretler). Kısmi tekil: `(apartment_id, person_id) WHERE is_current`. Bir dairede aynı anda en çok BİR güncel `owner` ve BİR güncel `tenant` olabilir (ikinci için 409 `RELATION_TAKEN`; `family_member`/`resident` çok olabilir).
- `apartments` EKLEMELİ kolonlar: `floor INTEGER NULL`, `gross_area_m2 NUMERIC(8,2) NULL`, `net_area_m2 NUMERIC(8,2) NULL` (m² sütunları KULLANIMDAN KALDIRILDI 2026-10-25, bkz. «Mimari Güncellemeler»; 078 migration'ı kalıcı düşürür), `land_share_numerator INTEGER NULL`, `land_share_denominator INTEGER NULL` (arsa payı kesri, ör. 35/1000; ikisi birlikte dolu ya da boş; payda > 0, pay ≤ payda), `category TEXT NULL` (daire tipi/kategorisi, ör. "3+1", "Dükkan"; ≤ 40 karakter), `responsible_party TEXT NOT NULL DEFAULT 'both' CHECK (owner|tenant|both)` ("borç ve bildirimler kime gitsin"; borç tarafını Faz 4 kullanır).
- `vehicles(id BIGSERIAL PK, site_code BIGINT NOT NULL REFERENCES sites ON DELETE CASCADE, person_id BIGINT NULL REFERENCES site_people ON DELETE SET NULL, apartment_id NULL, plate TEXT NOT NULL (normalize: büyük harf, boşluksuz), plate_display TEXT, note TEXT, is_active BOOLEAN NOT NULL DEFAULT TRUE, created_at)`; kısmi tekil `(site_code, plate) WHERE is_active`.
- `platform_backfills(code TEXT PRIMARY KEY, done_at TIMESTAMPTZ NOT NULL DEFAULT NOW())`.
- **Backfill `people_v1`** (ensureDbSchema içinde, tek sefer): her site için aktif `apartment_memberships` (aktif dairede) ve eski `apartments.resident_user_code` sakinleri → `site_people(user_code)` + `apartment_residencies(relation 'resident', is_current true, move_in_date = membership.created_at::date)`; aynı kişi birden çok dairede olabilir. Hiçbir `apartment_memberships`/kapı yetkisi satırına DOKUNMAZ. Sonrasında yeni üyelikler OKUMA/YAZMA anında `syncSitePeople(siteCode)` ile idempotent yansıtılır (listeleme ve kart uçları çağırır; mevcut katılım akışlarına kanca eklenmez). `syncSitePeople` hesapsız bir kişiyle aynı e-postaya sahip bir kullanıcı bulursa yinelenen kayıt açmak yerine o kişiye `user_code` bağlar (alanları `users`'a taşır).

## Sunucu uçları (hepsi `/manager/sites/:siteCode/...`, `requireSiteManager`'dan FARKLI olarak okuma `BOARD_MEMBER`'a da açık)

Yetki: yazma = yönetici/süper kullanıcı (`hasSiteManagementAccess`); okuma = yönetici/süper + `BOARD_MEMBER`; `STAFF` ve sakin 403 `FORBIDDEN_ROLE`; başka sitenin yöneticisi 403 `FORBIDDEN_SITE`. Hata gövdesi `{error, code}`. Tüm yazmalar audit'e yazılır (sonda eylem adları).

**Kişiler**
- `GET .../people?q=&relation=&status=active|inactive|all&apartment_id=&limit=50&offset=0` → `{ "items": [PersonSummary], "total": N }`. `q`: ad, telefon, e-posta, daire etiketi (büyük/küçük harf ve Türkçe karakter duyarsız). `relation`: kişinin GÜNCEL ilişkilerinden biri.
  `PersonSummary`: `{ id, full_name, phone, email, has_account, is_active, relations: ["owner"…], apartments: [{ apartment_id, label, block_name, relation }], vehicle_count }`.
- `GET .../people/:personId` → `PersonDetail`: Summary alanları + `note`, `created_at`, `residencies: [{ id, apartment_id, label, block_name, relation, is_current, move_in_date, move_out_date }]` (geçmiş dahil), `vehicles: [Vehicle]`, `user_code` (yalnız yönetici/süper için).
- `POST .../people` gövde `{ full_name, phone?, email?, note?, apartment_id?, relation?, move_in_date? }` → 201 `PersonDetail`. `full_name` zorunlu (2–100 karakter); e-posta/telefon doğrulanır. Aynı e-posta (aynı sitede aktif) → 409 `PERSON_EXISTS` (+ var olan `person_id`). **Hesap bağlama (inceleme kararıyla daraltıldı, bkz. "Faz 2a inceleme kararları"):** e-posta verilmişse ve bu e-posta kayıtlı bir kullanıcıya aitse VE o kullanıcının bu sitede zaten aktif bir bağı (üyelik) varsa kişi o kullanıcıya bağlanır (`has_account: true`) ve `apartment_id` varsa `apartment_memberships` kaydı (yoksa) oluşturulur/yeniden etkinleştirilir (rol: dairede aktif yönetici yoksa `APARTMENT_ADMIN`, varsa `FAMILY_MEMBER`; yönetici onayı gerekmez çünkü yönetici ekliyor); başka sitenin kullanıcısına ASLA bağlanılmaz ve üyelik açılmaz (kişi hesapsız kaydedilir, yanıt şekli aynıdır); hesap YOKSA ve `apartment_id` + e-posta varsa mevcut "daire sakini hesabı oluştur ve e-posta gönder" akışı (apartment_service / `PATCH /manager/apartments/:id/resident` mantığı) YENİDEN KULLANILIR — yeni bir davet/e-posta mekanizması icat edilmez; e-posta yoksa yalnız kayıt tutulur (`has_account: false`).
- `PATCH .../people/:personId` gövde `{ full_name?, phone?, email?, note?, is_active? }`. Kişinin kendi hesabında `full_name/phone` (ve gerçek hesapta `email`) gönderilirse 409 `PERSON_HAS_ACCOUNT` ("Hesabı olan kişinin bilgileri kişinin kendi profilinden değişir."); sitenin yönettiği hesapta `full_name/phone` hesabın kendisine (`users.full_name/phone_number`) yazılır (kişi kartında `identity_editable: true`; hesabı kilitleyen karar `people_service.isSiteManagedAccount`, kilit sırası apartments → users → site_people); `note` ve `is_active` her zaman. `is_active:false` → tüm güncel ilişkileri bitirir (aşağıdaki "taşınma" kuralları).
- **İlişkiler:** `POST .../people/:personId/residencies` `{ apartment_id, relation, move_in_date? }` → 201 `PersonDetail`; `PATCH .../residencies/:residencyId` `{ relation?, move_in_date? }`; `POST .../residencies/:residencyId/end` `{ move_out_date? }` ("Taşındı": `is_current=false`, tarih = verilen ya da bugün; kişinin hesabı varsa o dairedeki `apartment_memberships` satırı `is_active=false` yapılır → kapı yetkisi KAPANIR; başka dairedeki üyelikleri etkilenmez; satır silinmez). Başka sitenin dairesi 404 `APARTMENT_NOT_FOUND`.

**Daireler**
- `GET .../apartments?block_id=&q=&limit=&offset=` → `{ "items": [ApartmentSummary], "total": N }`: `{ id, label, block_id, block_name, floor, category, gross_area_m2 (m² kaldırıldı: yalnız eski istemci uyumu için durur, HEP null), net_area_m2 (HEP null), land_share:{numerator,denominator}|null, responsible_party, owner:{person_id,full_name}|null, tenant:{…}|null, resident_count }`.
- `GET .../apartments/:apartmentId` → `ApartmentDetail`: Summary + `current_residents: [{ residency_id, person_id, full_name, relation, move_in_date, has_account }]`, `past_residents: [{ …, move_out_date }]`.
- `PATCH .../apartments/:apartmentId` gövde `{ floor?, land_share_numerator?, land_share_denominator?, category?, responsible_party? }` → `ApartmentDetail`. Mevcut `unit_label`/blok yapısı bu uçla DEĞİŞMEZ. Geçersiz değer 400 `INVALID_BODY` (alan adıyla).

**Araçlar**
- `GET .../vehicles?q=&person_id=&limit=&offset=` → `{ "items": [Vehicle], "total": N }`; `Vehicle`: `{ id, plate, plate_display, note, person_id, person_name, apartment_label, is_active }`.
- `POST .../vehicles` `{ person_id, plate, note? }` → 201 `{vehicle}`; plaka Türk plakası olmalıdır (il kodu 01-81 + 1-3 harf + 2-4 rakam; kural `server/src/modules/plate_format.js`), normalize edilir (`34 ABC 123` → `34ABC123`, `plate_display` = `34 ABC 123`), aksi 400 `PLATE_INVALID` "Plaka biçimi geçersiz. Örnek: 34 ABC 123 (il kodu 01-81)." Yalnız YENİ yazılan plaka doğrulanır; eskiden 5–10 harf / rakam yeterdi, kayıtlı eski plakalar okuma / liste / kaldırmayı bozmaz; aynı sitede aktif aynı plaka 409 `PLATE_EXISTS`. `DELETE .../vehicles/:vehicleId` → `is_active=false` (kayıt kalır), `{ "ok": true }`.

**Geçmiş (F2.11)**
- `GET .../history?target_type=person|apartment|vehicle&target_id=&limit=50&before_id=` → `{ "items": [AuditItem], "next_before_id": N|null }`; yalnız O SİTENİN kayıtları (`audit_log.site_code`); `AuditItem` süper kullanıcı denetim kaydıyla aynı biçim (+ `details.changes: [{ "field": "phone", "from": "…", "to": "…" }]` değişen alanlar için). Yönetici ve kurul üyesi okur.

**Sakin (kendi kayıtları, F2.10)**
- `GET /app/my-records` (authRequired) → `{ "records": [ { site_code, site_name, apartment_id, label, block_name, relation, move_in_date, vehicles: [Vehicle] } ] }`: yalnız çağıranın kendi güncel kayıtları; başkasının bilgisi asla.

**Audit eylemleri** (`target_type`/`target_id`): `person.created`, `person.updated` (details.changes), `person.deactivated`, `residency.added`, `residency.updated`, `residency.ended`, `apartment.updated`, `vehicle.added`, `vehicle.removed`; hepsinde `site_code` dolu. `GET /admin/audit-log?action=` bunları da süzer.

**Hız sınırları:** yazma uçları kullanıcı başına ~120/saat; arama/liste uçlarında makul (örn. 600/saat).

## Faz 2a inceleme kararları (üç bağımsız inceleme sonrası; yukarıdaki metne göre ÖNCELİKLİDİR)

1. **Hesap bağlama yalnız sitenin kendi üyeleriyle.** `POST .../people` e-postayı tüm kullanıcılar arasında aramaz: bağlama yalnız o sitede zaten aktif bir bağı olan kullanıcıyla yapılır; aksi halde kişi hesapsız kaydedilir ve yanıt şekli hesabın var olup olmamasına göre DEĞİŞMEZ (hesap var/yok bilgisi sızmaz; başka sitenin ad/telefon/`user_code` alanı hiçbir yolla dönmez). `@ahbu.local` dahili adresler e-posta eşlemesinden dışlanır. Hesapsız kişi sonradan siteye katılım akışıyla üye olursa `syncSitePeople` e-posta eşlemesiyle hesaba bağlar. Hesaba bağlı kişide `site_people.full_name/phone` NULL'dır; tek istisna: hesap silinirken tetikleyici ad/telefonu yedekler (madde 2).
2. **Hesap silme / sıfırlama CRM'i bozmaz.** `users` için BEFORE DELETE tetikleyicisi (migration 031 ve `ensureDbSchema` aynı DDL): silinen kullanıcının `site_people` satırlarına ad/telefonu yedekler, e-postayı temizler, kişiyi pasifleştirir ve güncel ilişkilerini bitirir; silmeyi asla engellemez. Eşitleme yetim (`user_code IS NULL AND full_name IS NULL`) aktif kişileri "Sistem" adına pasifleştirir.
3. **"Taşındı" kapıyı gerçekten kapatır.** Kapanış mevcut üye çıkarma yan etkilerini yeniden kullanır (override temizliği, `APARTMENT_ADMIN` devri, dahili hesabın erişimi), daire kilidini önce alır, `move_out_date` gelecekte olamaz (400 `INVALID_BODY`). Hiç güncel ilişkisi kalmayan kişinin araçları pasifleşir (plaka serbest kalır, kayıt silinmez).
4. **İlişki kaynağı.** `apartment_residencies.origin` (`manual|sync`, API'ye çıkmaz): otomatik bitirme yalnız `sync` ilişkilere ve destekleyen üyelik/hesap gerçekten kalktığında uygulanır; geçici pasife alma (`is_active=false`) ilişkiyi bitirmez; elle girilen ilişkiler yalnız açık "Taşındı"/pasifleştirmeyle ya da eski ekrandan açık üye çıkarmayla ("Daireden çıkar", "Sakini Daireden Sil") biter.
5. **Rol kuralı.** CRM erişim verirken dairede aktif yönetici yoksa `APARTMENT_ADMIN` verilir (mevcut onay akışıyla aynı gösterge), aksi halde `FAMILY_MEMBER`. İSTİSNA (kullanıcı kararı 2026-10-26, migration 081): erişim verilen kişi dairenin güncel KİRACISIYSA (hesabı sonradan bağlanan dahil) mevcut admin malik olsa bile yönetim kiracıya geçer (`grantApartmentAccess` kancası; kişi kartından / daire ekranından kiracı ekleme ve ilişkiyi kiracıya çevirme ayrıca `ensureTenantIsAdmin` çağırır); kiracı ayrılırken (çıkış, «Taşındı», «Daireden çıkar», «Sakini sil», pasife alma) yönetim MALİKE döner: yönetim devri `handOverApartmentResident` kalan üyeyi güncel kiracı > güncel malik > en eski aktif üye sırasıyla seçer (`apartment_admin_successor.js`). Bkz. `docs/PLATFORM_DAIRE_YONETIMI.md` «Kiracı her zaman daire admini».
6. **Geçmiş gizliliği.** `details.changes`: telefon, e-posta ve not alanları için yalnız `{ "field", "changed": true }` (eski/yeni değer saklanmaz); ad ve sayısal/kategori alanlarında `from/to` olabilir. Sistem kayıtlarında `actor_name` "Sistem", `details.auto` true olabilir.
7. **Sakin ucu.** `/app/my-records` araç `note` alanını içermez.
8. **Dahili hesap kişisi.** `account_kind: 'internal'|'registered'|'none'` eklenir; `internal` kişide iletişim e-postası `apartments.resident_email`'den okunur ve CRM'den düzenlenebilir, ad/telefon salt okunurdur; `registered`te üçü de 409 `PERSON_HAS_ACCOUNT`.
9. **Kişi ekleme yanıtı.** `credentials_sent: true|false|null` (dahili hesap açıldıysa e-posta sonucu); `PERSON_EXISTS` yanıtında geçerli `person_id` ya da hiç yok (0 dönmez).
10. **Daire azaltma.** Mevcut özellik bozulmaz; CRM kaydı olan daireler silinirken `apartment.deleted` audit anlık görüntüsü yazılır (etiket, alanlar, ilişkiler, araç sayısı).
11. **Okuma yükü.** Okuma uçlarındaki eşitleme `pg_try_advisory_xact_lock` ile meşgulse atlanır ve site+kullanıcı başına kısa süre kısıtlanır; `/app/my-records` da okuma hız sınırına tabidir.

12. **"Sitede bağ" tek tanım.** Hesaba bağlama ve kapı erişimi verme için tek yardımcı (`siteTiePredicate`): bu sitenin aktif dairesinde aktif `apartment_memberships` satırı ya da `apartments.resident_user_code` göstergesi, ve hesap aktif. `site_memberships` (STAFF/BOARD_MEMBER/RESIDENT) ve yöneticilik tek başına bağ SAYILMAZ (yönetici onaysız STAFF atayarak başkasının hesabını bağlayamaz). Bağ yoksa kişi hesapsız ilişki olarak eklenir.
13. **Kişi pasifleşince hesaptan kopar.** Kişinin güncel ilişkisi kalmadığında VE kullanıcının sitede başka aktif bağı yoksa: kişi pasif olur, ad/telefon/e-posta anlık kopyalanır, `user_code` NULL olur (eski siteye taşınanın sonradan değiştirdiği telefon görünmez), araçları pasifleşir. Kullanıcının sitede aktif bağı sürüyorsa (ör. başka daireye onaylı katılım henüz CRM'e yansımamışsa) kişi aktif ve bağlı kalır. Aynı kişi sonradan yeniden üye olursa eşitleme YENİ aktif kayıt açar; eski satır pasif geçmiş olarak kalır. Pasif kişiyi etkinleştirme/ilişki ekleme yalnız bağ kuralına göre hesaba bağlar; çakışma 409 `PERSON_EXISTS`. Pasif dahili hesap `has_account:false`/`account_kind:'none'`.
14. **Eski ekranlardan üye çıkarma CRM'e yansır.** "Daireden çıkar" ve "Sakini Daireden Sil" aynı transaction'da o (kullanıcı, daire) çifti için güncel ilişkileri (her iki `origin`) bitirir (audit yapan yönetici adına). Geçici pasife alma (`toggleApartmentMemberStatus`, daire askıya alma) ilişkiyi BİTİRMEZ.
15. **Taşındı yönetici devri.** Devir yalnız göstergenin sahibi (legacy) ya da aktif `APARTMENT_ADMIN` çıkarken yapılır; gösterge başkasındaysa yalnız admin rolü devredilir, dairedeki diğer sakinin göstergesi/PIN'i/kapı erişimi korunur.
16. **Kilit sırası.** apartments (id sırasıyla) → users → site_people/apartment_residencies/vehicles; CRM yazma işlemleri 40P01'de tek seferlik yeniden denenir; kullanıcı silme ve "Daire sakinini sıfırla" daire kilidini ÖNCE alır.
17. **Kurul yanıtları.** `note` (kişi, araç), `user_code`, `created_by`, `actor_user_code` kurul üyesine hiçbir yanıt yolunda verilmez.

## Yönetim kadrosu ve uygulamaya davet (migration 058, 2026-10-21)

**Tablolar** (`team_schema.js` = `058_team_and_invitations.sql`, FK'sız tablo + ayrı katalog korumalı FK): `site_team_duties` (kişi başına TEK etkin görev; `duty` board_member / auditor / doorman / technical / reception / other, `other` için unvan zorunlu, `public_phone` yalnız `+90XXXXXXXXXX`, `show_in_directory`, `ended_at`), `site_directory_contacts` (faydalı telefonlar, site başına en çok 100), `person_invitations` (belirteç YALNIZ SHA-256 özeti; kapanan davette `email` ve `token_hash` NULL; kişi başına tek bekleyen davet).

**Kadro uçları** (yazma yönetici/süper; okuma + kurul; STAFF/sakin 403; başka site 403): `GET /manager/sites/:siteCode/team` (yönetici adları, görevler, eski ek roller, telefonlar; kurul e-posta, user_code, erişim durumu ve eski rolleri GÖRMEZ), `PUT|DELETE .../people/:personId/duty`. Görev kişi kaydına bağlıdır, hesap şart değildir; kişinin KENDİ kayıtlı, etkin, doğrulanmış (dahili olmayan) hesabı varsa aynı işlemde `site_memberships` yazılır (board_member / auditor -> BOARD_MEMBER, diğerleri -> STAFF; SITE_OWNER/ADMIN korunur). `access`: granted | no_account | invited | internal_account | manager | needs_sync. Yönetici kişiye 409 `ALREADY_SITE_MANAGER`. Görev bitince üyelik dairede aktif üyeliği varsa RESIDENT'a düşer, yoksa silinir. Audit: `team.duty_assigned` / `team.duty_ended`.

**Davet** (`person_invite_service.js`): `GET|POST|DELETE .../people/:personId/invitation`. Yalnız `account_kind = none`, e-postalı, aktif kişi (409 PERSON_NO_EMAIL / PERSON_HAS_ACCOUNT / PERSON_INTERNAL_ACCOUNT / PERSON_INACTIVE); SMTP yoksa 503 ve hiçbir şey yazılmaz. Belirteç 32 bayt CSPRNG, 7 gün, tek kullanım; yeniden gönderim eskisini geçersiz kılar; bağlantı yanıtta ASLA dönmez. Sınırlar: kullanıcı 30/saat, site 200/gün, kişi için 60 sn bekleme ve en çok 5 gönderim. E-posta işlem bittikten sonra gider (hata -> `sent:false`). Kabul: `GET|POST /auth/accept-invite` (CSP `default-src 'none'`, no-store, no-referrer) yeni hesap açar (doğrulanmış hesap varsa 409 `ACCOUNT_EXISTS`: uygulamada giriş + Kabul et; bekleyen kayıt silinir, doğrulanmamış eski satır sahiplenilir), kişiyi bağlar, güncel ilişkiler için daire erişimi ve görev üyeliğini verir, onayları `source='invite'` yazar. Mevcut hesap: `GET /app/invitations`, `POST /app/invitations/:id/accept|decline` (doğrulanmış e-posta eşleşmesi; bu sitede başka kişi kaydı varsa 409 `INVITE_PERSON_CONFLICT`). Geçersiz / dolmuş / kullanılmış belirteç tek tip 400 `INVITE_INVALID`. Kabulde kişi hâlâ aktif, hesapsız ve e-postası davetteki ile aynı olmalıdır (e-posta değişimi / pasifleşme daveti fiilen geçersiz kılar); bakım (`runDatabaseCleanup`) dolanı `expired`, bağlanmış / pasif kişinin bekleyenini `revoked` yapar. Kilit sırası: `email_verify:<e-posta>` -> `people_sync:<site>` -> davet satırı.

**Kararlar / sınırlar.** Boş dairede bugünkü daire hesabı + PIN akışı DEĞİŞMEDİ; dahili daire hesabına davet / görev yetkisi yok. Eski `PUT /staff-roles` uç davranışı aynen duruyor (kişi kaydı olmayan hesaba e-postayla rol; numaralandırma riski kabul edilmiş durumda, daraltma sonraya).
