# İş Takibi (arıza, bakım, talep) - sunucu sözleşmesi

Modül kodu `work_tracking` (katalogda `available`, varsayılan KAPALI; süper açar, yönetici modül talep eder). Kapalıyken tüm uçlar `403 MODULE_DISABLED` (`module: "work_tracking"`; sakin listesi site_code'suz ise o siteyi atlar, tek talep 404). Fotoğraf ekleri (JPEG/PNG/WebP, migration 047) vardır (bkz. "Fotoğraf ekleri"); başka dosya türü YOK; e-posta/push YOK (yalnız uygulama içi `unread`). Hata gövdesi her yerde `{ error, code, ...ek }`; kimlik `Authorization: Bearer`.

## Veri modeli (migration 042 + 047)
- `work_items`: id, site_code, category, location_type, title (1-120), description (1-2000), apartment_id?, block_id?, status, priority, resident_urgent, assigned_to?, due_date?, created_by?, created_at, updated_at, closed_at?, requester_seen_at, resident_updated_at.
- `work_item_events` (değişmez günlük, yalnız eklenir): work_item_id, event_type, visibility (`public|internal`), actor_user_code?, actor_kind (`resident|staff|manager`), from_value?, to_value?, body? (yorum, 1-1000). 047 ile `event_type` kümesine `attachment_added|attachment_removed` eklendi (CHECK kısıtı genişletildi).
- `work_item_attachments` (047): id, work_item_id (CASCADE), site_code (CASCADE), uploaded_by? (users SET NULL), file_name (1-160), mime_type (`image/jpeg|image/png|image/webp`), size_bytes (1..5242880), sha256?, status (`uploading|ready`), storage_key? (sunucuya ait `<site_code>/<uuid>`), created_at, ready_at?.
- Sabit değerler: category `ariza|bakim|sikayet_oneri|diger`; location_type `ortak_alan|daire`; status `yeni|islemde|beklemede|cozuldu|kapandi|iptal`; priority `dusuk|normal|acil`.
- Hesap silinince talep/olaylar/yorum metinleri/fotoğraflar KALIR; açan/yazan/yükleyen adı "Silinmiş Kullanıcı"; silinen görevlinin AÇIK talepleri atamasız kalır (kapalı talepler geçmiş olarak atanmış kalır). Site silinince hepsi silinir (fotoğraf dosyalarını bakım işi süpürür). Dışa aktarmada yalnız kullanıcının kendi talepleri (`work_items_created`: başlık/açıklama/durum/tarih), kendi yazdığı yorumlar (`work_item_comments`: work_item_id, created_at, body, visibility) ve kendi eklediği fotoğrafların kayıt bilgisi (`work_item_attachments_uploaded`: id, work_item_id, site_code, file_name, mime_type, size_bytes, status, created_at; görüntü içeriği / depolama anahtarı / sha256 YOK) bulunur.

## Durum geçişleri (sunucuda doğrulanır; `next_statuses` yönetim detayında hazır gelir)
yeni -> islemde, beklemede, cozuldu, iptal | islemde -> beklemede, cozuldu, iptal | beklemede -> islemde, cozuldu, iptal | cozuldu -> kapandi, islemde (yeniden aç) | kapandi, iptal SONDUR (değişiklik/yorum/fotoğraf yok: 409 WORK_ITEM_CLOSED, fotoğrafta 409 INVALID_STATE). Sakin yalnız KENDİ `yeni` talebini `iptal` eder.

## Uçlar
Sayfalama: `before_id` imleci + `limit` (1-100, varsayılan 30); yanıttaki `next_before_id` doluysa sonraki sayfa. Sıra id azalan. Tüm yazan uçlar JSON gövde (≤16 KB); tek istisna fotoğraf İÇERİĞİ (ham gövde, aşağıda).

| Uç | Gövde / sorgu | Yanıt |
|---|---|---|
| GET `/app/work-items` | `site_code?`, `status=open\|closed\|all`, `before_id`, `limit` | `{ items:[MyItem], next_before_id, unread_updates }` |
| POST `/app/work-items` (201) | `site_code, category, location_type, title, description, apartment_id?, block_id?, urgent?(bool), idempotency_key` | `{ item:MyItem, replayed }` |
| GET `/app/work-items/:id` | - | `{ item:MyItem, events:[Event], attachments:[Attachment] }` (yalnız public) |
| POST `/app/work-items/:id/cancel` | - | `{ item }` |
| POST `/app/work-items/:id/comments` (201) | `body, idempotency_key` (public) | `{ event, replayed }` |
| POST `/app/work-items/:id/seen` | - | `{ id, unread:false }` |
| POST `/app/work-items/:id/attachments` (201) | `file_name, mime_type, size_bytes` | `{ attachment:Attachment }` (`status:"uploading"`) |
| PUT `/app/work-items/:id/attachments/:attId/content` | ham gövde `application/octet-stream`, `Content-Length` = `size_bytes` | `{ attachment:Attachment }` (`status:"ready"`, `ready_at`) |
| GET `/app/work-items/:id/attachments/:attId/content` | - | görüntü baytları (başlıklar aşağıda) |
| DELETE `/app/work-items/:id/attachments/:attId` | - | `{ deleted:true }` |
| GET `/manager/sites/:siteCode/work-items` | `status` (virgüllü ya da `open`), `category`, `priority`, `assigned=me\|none\|<user_code>`, `q`, `before_id`, `limit` | `{ items:[Item], next_before_id, counts:{yeni,...,iptal} }` |

`idempotency_key`: 8-64 karakter `[A-Za-z0-9_.:-]`, istemci üretir; aynı anahtar + AYNI içerik (talep: başlık/açıklama/kategori/konum/urgent; yorum: body+visibility) yeni satır açmaz, aynı kaydı döner (`replayed:true`); aynı anahtar + FARKLI içerik `409 IDEMPOTENCY_CONFLICT`. Sakin daire yalnız KENDİ güncel dairesi olabilir; `ortak_alan` talebinde daire gönderilemez; blok sitenin bloğu olmalı.

## Yanıt şekilleri
- **MyItem** (sakin): id, site_code, site_name, category, location_type, title, description, status, `urgent`, apartment{id,label}?, block{id,name}?, `has_assignee`(bool), due_date?, created_at, updated_at, closed_at?, `unread`, `can_cancel`, `can_comment`, `attachment_count` (hazır fotoğraf sayısı). Öncelik, atanan adı ve iç olaylar sakine GÖSTERİLMEZ.
- **Item** (yönetim; sakin görünümünden FARKLI alanlar): id, site_code, category, location_type, title, description, status, priority, resident_urgent, apartment?, block?, `requester{user_code,name,phone?}`, `assigned_to{user_code,name}?`, due_date?, created_at, updated_at, closed_at?, `attachment_count`. KURUL için `requester` yalnız `{name}` (telefon ve kullanıcı kodu yok).
- **Event**: id, type (`created|status_changed|assigned|priority_changed|due_date_changed|comment|attachment_added|attachment_removed`), visibility, actor_kind, from, to, body, created_at. `attachment_added` (to = ek kimliği) ve `attachment_removed` (from = ek kimliği) public'tir (sakin de görür). Yönetim görünümünde `actor{user_code,name}` ve `assigned` olaylarında `from_label/to_label` da gelir; sakin/kurul görünümünde `actor_kind` yalnız `resident|management`, iç (internal) olaylar (atama, öncelik, iç yorum) HİÇ gelmez. `unread`: yönetim sizin görmediğiniz bir durum/hedef tarih/herkese açık yorum/fotoğraf yazdıysa true; detayı açınca `.../seen` çağrılır. Sakinin KENDİ eylemleri (iptal, yorum, fotoğraf) okunmamış işareti bırakmaz.
- **Attachment**: id, work_item_id, file_name, mime_type, size_bytes, status (`uploading|ready`), `uploaded_by_kind` (`resident`: yükleyen talebi AÇAN kişi; `management`: diğer herkes — yönetici / süper / görevli; yükleyen hesabı fiziksel silinmişse de `management`), uploaded_by_name, uploaded_by_me (bool), created_at, ready_at?. Detaydaki `attachments`: hazır ekler + çağıranın KENDİ, süresi dolmamış (2 saat) tamamlanmamış yüklemeleri (id sırası). `uploaded_by_name` görünüme göre (WA-SEC-1):
  - **Yönetim görünümü** (yönetici / süper / görevli / kurul): yükleyenin gerçek adı; silinmiş hesapta "Silinmiş Kullanıcı".
  - **Sakin görünümü** (`/app/...` ayrıntı, POST / PUT yanıtları): sakinin KENDİ eklediği fotoğrafta kendi adı (`uploaded_by_kind: resident`, `uploaded_by_me: true`); başkasının eklediği HER fotoğrafta `uploaded_by_name: "Yönetim"` (`uploaded_by_kind: management`, `uploaded_by_me: false`). Sakine yönetim tarafından hiçbir kişinin adı dönmez; bu alan sakin görünümünde null ya da "Silinmiş Kullanıcı" olmaz.

## Fotoğraf ekleri (047)
**Sınırlar:** talep başına en fazla 4 fotoğraf (hazır + yüklenmekte, tüm yükleyenler birlikte; `409 LIMIT_REACHED`, `attachment_limit`), fotoğraf ≤ 5 MB (`413 ATTACHMENT_TOO_LARGE`), tür yalnız `image/jpeg|image/png|image/webp` (`415 ATTACHMENT_TYPE_NOT_ALLOWED`), kullanıcı başına saatte 30 kayıt (siteler arası, son 1 saatte açılmış ve hâlâ duran kayıtlar sayılır: silinen kayıt sayıdan düşer, aç-sil döngüsünü HTTP yazma sınırı 120/saat ve PUT sınırı 60/saat keser; `429 WORK_ATTACHMENT_RATE_LIMITED` + `Retry-After: 3600`), yalnız açık talepte (kapandi/iptal: `409 INVALID_STATE`). **Bayt kotaları (WA-SEC-3, R2-2):** hazır + süresi dolmamış yüklemelerin `size_bytes` toplamı, gelen kaydın boyutu DAHİL. (1) **Sakin kotası** YALNIZ sakin kapsamına (`/app` uçları) uygulanır ve KAYAN 30 günlük penceredir: sakinin BU sitede `created_at` son 30 gün içinde olan kayıtlarının toplamı + gelen boyut ≤ `WORK_ATTACHMENTS_USER_QUOTA_MB` (varsayılan 200 MB); aşım `409 ATTACHMENT_QUOTA_EXCEEDED` `{ quota: "user", quota_bytes, used_bytes, window_days: 30 }`, ileti: "Son 30 günde bu sitede yükleyebileceğiniz fotoğraf sınırına ulaştınız (en çok 200 MB); daha sonra yeniden deneyin ya da yönetime başvurun." (MB değeri ayarlanan sınırdır). Görevli / yönetici / süper bu kotaya TABİ DEĞİLDİR; pencere sayesinde kapanan talepte kalan (sakinin artık silemediği) fotoğraflar kimseyi kalıcı olarak kilitlemez. Pencere sorgusu `(uploaded_by, created_at)` kısmi indeksini kullanır. (2) **Site kotası** herkese (yönetici dahil), pencere YOK: sitenin tüm fotoğrafları ≤ `WORK_ATTACHMENTS_SITE_QUOTA_MB` (varsayılan 10240 MB = 10 GB); aşım `409 ATTACHMENT_QUOTA_EXCEEDED` `{ quota: "site", quota_bytes, used_bytes }` ("Sitenin fotoğraf alanı doldu. Yönetimle iletişime geçin."). Kayıt açılmaz. Sakin toplamı kullanıcı kilidi, site toplamı site fotoğraf kilidi (`work_attachments_site:<kod>`) altında sayılır; eşzamanlı kayıtlar kotayı aşamaz. **Süresi dolan kayıtlar:** 2 saati aşan `uploading` kaydı bakım işi silmeden önce de talep sınırına (4) ve kotalara SAYILMAZ, ayrıntıda listelenmez (sahibi PUT atarsa `410 UPLOAD_EXPIRED`). **Piksel boyutu (açılma bombası koruması):** kenar en çok 12.000 piksel ve genişlik × yükseklik en çok 40.000.000; aşan fotoğraf `415 ATTACHMENT_DIMENSIONS_TOO_LARGE` `{ width, height, max_side, max_pixels }`. Dosya adı: yol parçaları atılır, 100 kod noktasına kesilir, uzantı istemciden DEĞİL bildirilen türden gelir (`foto.png` + `image/jpeg` -> `foto.jpg`); boş ad `fotograf`.

**İstemcide hazırlık (Flutter, `lib/services/work_photo_prepare.dart`):** seçilen her fotoğraf yüklenmeden ÖNCE uygulamada yeniden kodlanır: uzun kenar en çok 2560 piksele küçültülür (daha küçükse boyut korunur), JPEG kalite 85, saydam alan beyaza düzlenir, EXIF yön bilgisi uygulanır ve EXIF dahil TÜM üstveri (GPS konumu) atılır; dosya adı `.jpg`, tür `image/jpeg` olur. iOS'ta seçici Fotoğraflar (PHPicker, HEIC -> JPEG "compatible") açılır; diğer platformlarda jpg/jpeg/png/webp süzgeci kalır. En çok 50 MB'lık dosya okunur (büyüğü "çok büyük" notuyla reddedilir); çözme koruması: web'de ve PNG/WebP'de 40 M piksel / 12.000 kenar, yerel JPEG'de 64 M piksel (motor JPEG'i hedefe yakın küçük ölçekte çözer). Hazırlık başarısız olursa özgün bayt gönderilir ve sunucu kuralları karar verir. Sunucu sınırları (5 MB, 40 M piksel) değişmedi; başka istemciler (API) için de geçerlidir ve sunucu üstveriyi SİLMEZ.

**Akış (belgeler modülüyle aynı ilkeler, docs/PLATFORM_BELGELER.md A3/A4):** (1) `POST .../attachments` üstveriyi doğrular, `uploading` kaydı açar (201). (2) `PUT .../attachments/:attId/content`: `Content-Type: application/octet-stream` (aksi `415 INVALID_CONTENT_TYPE`), `Content-Length` ZORUNLU (yok/chunked `411 LENGTH_REQUIRED`) ve = `size_bytes` (aksi `400 ATTACHMENT_SIZE_MISMATCH`); yalnız kaydı açan kullanıcı yükler (başkasının kaydı 404). İlk 16 baytta içerik imzası kararı: tanınmayan `415 ATTACHMENT_TYPE_NOT_ALLOWED`, bildirilen türle uyuşmayan `415 ATTACHMENT_CONTENT_MISMATCH` (akış hemen kesilir, geçici dosya silinir, kayıt `uploading` kalır ve yeniden denenebilir); PNG için IHDR + IEND bütünlüğü; ardından piksel boyutu YALNIZ başlıktan okunur (PNG IHDR, WebP `VP8 ` / `VP8L` / `VP8X`, JPEG SOFn işaretçisi; görüntü sunucuda ÇÖZÜLMEZ): sınırı aşan `415 ATTACHMENT_DIMENSIONS_TOO_LARGE`, boyutu okunamayan / sıfır olan başlık `415 ATTACHMENT_CONTENT_MISMATCH` (ikisinde de geçici dosya silinir, kayıt `uploading` kalır ve aynı kayda doğru fotoğraf yüklenebilir). Biter: fsync -> `link` ile son yola (hazır dosya ASLA ezilmez) -> TEK DB işlemi: kayıt `ready` (+ sha256, ready_at), `attachment_added` olayı (public), audit `work_item.attachment_added`; yönetim eklediyse sakinin `unread` işareti düşer, sakin eklediyse düşmez. Aynı kayda eşzamanlı ikinci PUT `409 UPLOAD_IN_PROGRESS` (uçuştaki PUT anahtarı kullanıcı + kayıt, `wa:<kullanıcı>:<ek>`: başka kullanıcının PUT'u bu anahtara takılmaz, sahiplik denetiminde 404 alır; kaydın yüklenmekte olduğu sızmaz); tamamlanmış kayda PUT `409 UPLOAD_ALREADY_COMPLETED`; 2 saati geçen kayda PUT `410 UPLOAD_EXPIRED` (bakım işi bu kayıtları siler). Süreç genelinde en çok 8 eşzamanlı PUT (`503 UPLOAD_BUSY`, `Retry-After: 5`); depolama yoksa / disk doluysa `503 ATTACHMENT_STORAGE_UNAVAILABLE`. Ek hız sınırı: PUT kullanıcı başına 60/saat.
**İndirme:** `GET .../attachments/:attId/content` yalnız `ready` ek (değilse 404); `Content-Type` = DB'deki mime (asla istemcinin bildirdiği), `Content-Length`, `Content-Disposition: inline; filename="<ASCII>"; filename*=UTF-8''<ad>`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`; `Range` yok sayılır; dosya kayıpsa `500 ATTACHMENT_FILE_MISSING` (+ `errorId`). Eşzamanlı fotoğraf indirmesi 32 (`503 DOWNLOAD_BUSY`); fotoğraflar belgelerden AYRI yuva sayacı kullanır (fotoğraf indirmeleri belge indirme yuvalarını tüketemez, tersi de).
**Silme:** `DELETE .../attachments/:attId` -> `{ deleted:true }`; satır işlemde silinir, dosya COMMIT SONRASI (silinemezse günlüğe kod yazılır, yetim süpürmesi temizler). Hazır ek silinince `attachment_removed` olayı (public) + audit `work_item.attachment_removed` (`details`: attachment_id, status, mime_type, size_bytes, by, own, `closed_item`); tamamlanmamış kayıt olaysız kalkar (audit yine yazılır). **Kapalı (kapandi / iptal) talepte** fotoğraf EKLENEMEZ (herkes `409 INVALID_STATE`) ve yalnız yönetici / süper SİLEBİLİR (moderasyon / KVKK talebi; olay + audit aynen, `closed_item: true`); görevli ve sakin kendi fotoğrafını bile silemez (`409 INVALID_STATE`, mesaj: "Kapatılmış ya da iptal edilmiş talebe fotoğraf eklenemez; bu talepteki fotoğrafları yalnız yönetici silebilir."). Kurul her durumda `403 FORBIDDEN_ROLE`. (WA-SEC-2)

**Yetki (talebi görebilen ek listesini görür ve indirir):**
| Rol | Ekle (POST + PUT; yalnız açık talep) | Gör / indir | Sil (açık talep) | Sil (kapandi / iptal talep) |
|---|---|---|---|---|
| Sakin | yalnız KENDİ talebine (hâlâ aktif sakinken) | kendi talebindeki hepsi (başkasının eklediğinde ad "Yönetim") | yalnız kendi eklediğini | hayır (`409 INVALID_STATE`) |
| Görevli | kapsamındaki (kendine atanmış / atanmamış / yetim atamalı) taleplere | kapsamındaki | yalnız kendi eklediğini (başkasınınki `403 FORBIDDEN_ROLE`) | hayır (`409 INVALID_STATE`) |
| Yönetici / Süper | sitenin tüm taleplerine | hepsi | hepsini | hepsini (olay + audit `closed_item: true`) |
| Kurul | hayır (`403 FORBIDDEN_ROLE`) | hepsi | hayır (403) | hayır (403) |

IDOR: ek talebe, talep siteye / açana ait değilse `404 WORK_ITEM_NOT_FOUND` / `404 WORK_ATTACHMENT_NOT_FOUND` (varlık sızmaz). Audit `details` yalnız kimlik / tür / boyut taşır; dosya adı yazılmaz; sunucu günlüğüne dosya adı yazılmaz.

**Depolama:** `<DOCUMENTS_DIR>/work_attachments/<site_code>/<uuid>` (belgelerin `sites/` ağacından AYRI; aynı `_tmp/`, aynı anahtar biçimi ve traversal kuralları, dosya 0600 / dizin 0700, `storage_key` sunucuya ait). Bakım (saatlik `document_maintenance`, tek çalışan kilidi): 2 saati aşan `uploading` kayıtları ÖNCE satır SONRA dosya silinir; DB'de satırı olmayan dosyalar `WORK_ATTACHMENTS_ORPHAN_MIN_AGE_DAYS` (varsayılan 30 gün) yaşından SONRA SİLİNİR (karantina yok; yaş güvenlik payıdır: yedekten dönüşte DB'si dosyadan eski kalan fotoğraflar bir ay korunur; oran koruması: >20 ve >%50 yetim görünüyorsa durur); silinmiş sitelerin `work_attachments/<kod>` dizinleri 7 gün sonra kaldırılır (seyrek ağaç koruması: silinecek dizin sayısı > 5 VE tüm site dizinlerinin > %50'si ise durur; DB'de hiç site yoksa hiç silmez); disk kaynaklı silmeler yalnız depolama kimliği doğrulanınca çalışır. Yedek: `backup_db.sh` fotoğrafları belgelerden AYRI şifreli arşive alır (`kapi_work_attachments_<TS>.tgz.enc`: `work_attachments/` + `.instance`; kendi boyut sınırı `WORK_ATTACHMENTS_BACKUP_MAX_MB` 3000, özeti, tutma adedi `KEEP_WORK_ATTACHMENTS` 5, yaş sınırı 210 gün, dış kopya; sembolik bağlantı olan dizin reddedilir; başarısızlık yedek e-postasında ayrı sonuç olarak FAIL verir); `restore_test.sh` geri yüklenen DB'deki hazır fotoğrafların bu arşivde olduğunu doğrular (bkz. docs/OPERASYON_YEDEK_IZLEME.md). **Nginx:** `client_max_body_size` varsayılanı 1 MB'tır; fotoğraf içerik yolları için ayrı `location` bloğu gerekir (belgelerdeki kalıpla, `client_max_body_size 6m`): `location ~ ^/app/work-items/[0-9]+/attachments/[0-9]+/content$` ve `location ~ ^/manager/sites/[0-9]+/work-items/[0-9]+/attachments/[0-9]+/content$`; aksi hâlde 1 MB üstü fotoğraf Nginx'te 413 (HTML) ile kesilir.

**Hesap silme / dışa aktarma:** fotoğraf kaydı ve dosyası taleple kalır. Hesap silme kullanıcı satırını SİLMEZ, kimliksizleştirir: `uploaded_by` belgelerdeki `document_versions.uploaded_by` gibi kimliksizleştirilmiş (tombstone) hesaba bağlı kalır ve yükleyen adı her görünümde "Silinmiş Kullanıcı" olur; kullanıcı satırı fiziksel olarak silinirse FK `ON DELETE SET NULL` ile NULL olur (ad yine "Silinmiş Kullanıcı"). Önizleme `will_keep`: `İş takibi taleplerine eklediğiniz fotoğraflar (N) taleple birlikte site yönetiminde kalır; yükleyen adı "Silinmiş Kullanıcı" görünür.` Dışa aktarma bölümü `work_item_attachments_uploaded` (en çok 500 kayıt, kısaltılabilir); görüntü içeriği dosyaya konmaz (`excluded` notu). Süper kullanıcının kalıcı silmesinde (`DELETE /admin/users/:id`, gerçek `DELETE FROM users`) aynı işlemde önce kullanıcı satırı kilitlenir (`FOR UPDATE`), sonra hesap silmeyle AYNI yardımcılarla kişiye atanmış açık talepler bırakılır (her biri için iç `assigned` olayı) ve gelecekteki rezervasyon / açık konsiyerj kayıtları sistemce iptal edilir; kullanıcı satırı en son silinir (fotoğraf satırlarında `uploaded_by` FK ile NULL olur).

## Performans raporu (yönetici / süper / kurul; görevli `403 FORBIDDEN_ROLE`)
`GET /manager/sites/:siteCode/work-items/report?from=YYYY-MM-DD&to=YYYY-MM-DD` — tarihler Europe/Istanbul takvim günleri, iki uç dahil; verilmeyen uç: `to` = bugün, `from` = bugün - 29 (30 gün). `from > to`, 366 günden uzun aralık ya da geçersiz tarih `400 INVALID_FIELD`. Yanıt:
```
{ from, to, generated_at,
  totals: { opened, resolved, closed, cancelled, open_now, overdue_now, avg_resolution_hours|null, median_resolution_hours|null },
  by_assignee: [{ user_code|null, name, open_now, overdue_now, resolved, avg_resolution_hours|null, on_time_rate|null }],
  by_category: [{ category, opened, resolved }] }   // 4 kategori her zaman, sıfırlarla
```
Tanımlar: **opened** = `created_at` aralıkta; **resolved** = talebin İLK `status_changed -> cozuldu` olayı (hiç cozuldu olmadıysa ilk `-> kapandi`) aralıkta, çözüm süresi = o olay anı - `created_at` (saat, 1 ondalık; ortalama ve medyan); **closed / cancelled** = `closed_at` aralıkta ve güncel durum kapandi / iptal; **open_now** = durum cozuldu/kapandi/iptal dışında (şu an); **overdue_now** = open_now ve `due_date` < bugün; **on_time_rate** = çözüm günü <= `due_date` olanların, `due_date` dolu çözülmüşlere oranı (0..1, 3 ondalık; hiç yoksa null). **by_assignee**: open_now / overdue_now GÜNCEL `assigned_to`ya göre; resolved / süre / zamanında oranı ÇÖZÜM ANINDAKİ atanana göre: (1) çözüm olayından önceki (ya da aynı işlemde, aynı anda yazılan) son `assigned` olayının hedefi (`to`); (2) yoksa çözümden SONRAKİ ilk `assigned` olayının kaynağı (`from`; çözüm anında kim atanmışsa o — atanmamışken çözülüp sonra atanan talep "Atanmamış" kovasında kalır); (3) talepte hiç atama olayı yoksa güncel `assigned_to`. Olay değerleri güvenli tamsayı dönüşümüyle okunur (sayı olmayan / taşan değer = atanmamış). Sonradan devredilen talep çözen kişide kalır; tek PATCH ile devir + `cozuldu` yeni atanana yazılır. Atanmamış kova `user_code: null, name: "Atanmamış"` listenin sonunda; silinmiş hesap "Silinmiş Kullanıcı"; diğerleri ada göre (tr) sıralı. Tüm sayımlar SQL'de toplanır (GROUPING SETS; satır başına JS döngüsü yok); mevcut indeksler yeterlidir (site + olay indeksleri), yeni indeks eklenmedi.

## Hata kodları
400: `INVALID_BODY` (alan Türkçe etiketle), `INVALID_QUERY`, `INVALID_SITE_CODE`, `INVALID_ASSIGNEE`, `INVALID_LOCATION`, `INVALID_FIELD` (rapor tarihleri), `ATTACHMENT_SIZE_MISMATCH`. 401 `ACCOUNT_DELETED`. 403: `MODULE_DISABLED`, `FORBIDDEN_ROLE`, `FORBIDDEN_SITE`, `NOT_A_RESIDENT`. 404: `WORK_ITEM_NOT_FOUND`, `WORK_ATTACHMENT_NOT_FOUND`, `SITE_NOT_FOUND`. 409: `INVALID_TRANSITION` ({from,to}), `WORK_ITEM_CLOSED`, `WORK_ITEM_LIMIT` (sitede açık talep üst sınırı, `open_limit`), `WORK_ITEM_USER_LIMIT` (kişinin o sitede açık talebi, `user_open_limit`), `WORK_ITEM_COMMENT_LIMIT` (sakin 100, yönetim/görevli 200 yorum; ayrı sayılır), `IDEMPOTENCY_CONFLICT`, `LIMIT_REACHED` (talep başına 4 fotoğraf, `attachment_limit`), `ATTACHMENT_QUOTA_EXCEEDED` (`quota: "user"|"site"`, `quota_bytes`, `used_bytes`; `user` için ayrıca `window_days: 30`), `INVALID_STATE` (kapalı talebe fotoğraf ekleme; kapalı talepte yönetici / süper dışında silme), `UPLOAD_IN_PROGRESS`, `UPLOAD_ALREADY_COMPLETED`. 410 `UPLOAD_EXPIRED`. 411 `LENGTH_REQUIRED`. 413 `BODY_TOO_LARGE`, `ATTACHMENT_TOO_LARGE`. 415 `INVALID_CONTENT_TYPE`, `ATTACHMENT_TYPE_NOT_ALLOWED`, `ATTACHMENT_CONTENT_MISMATCH`, `ATTACHMENT_DIMENSIONS_TOO_LARGE` (`width`, `height`, `max_side` 12000, `max_pixels` 40000000). 429: `WORK_ITEM_RATE_LIMITED` (`Retry-After`; kullanıcı saatte 20 talep, siteler arası toplam), `WORK_ATTACHMENT_RATE_LIMITED` (saatte 30 fotoğraf kaydı) ve genel hız sınırı (yazma 120/saat, okuma 1200/saat, fotoğraf PUT 60/saat). 500 `ATTACHMENT_FILE_MISSING`. 503 `ATTACHMENT_STORAGE_UNAVAILABLE`, `UPLOAD_BUSY`, `DOWNLOAD_BUSY`.

## Sınırlar (ortam değişkeni)
`WORK_ITEMS_MAX_OPEN_PER_SITE` (2000; kapandi/iptal dışı talepler), `WORK_ITEMS_MAX_PER_USER_PER_HOUR` (20; siteler arası), `WORK_ITEMS_MAX_OPEN_PER_USER` (30; kişinin tek sitede açık talebi). Fotoğraf: `WORK_ATTACHMENTS_USER_QUOTA_MB` (200; YALNIZ sakin: bir sitede son 30 günde açtığı fotoğrafların toplamı; pencere sabit 30 gün), `WORK_ATTACHMENTS_SITE_QUOTA_MB` (10240; sitenin toplamı), `WORK_ATTACHMENTS_ORPHAN_MIN_AGE_DAYS` (30; yetim dosya silme yaşı) — her istekte / bakım turunda okunur, geçersiz değer varsayılana döner (uyarı yalnız ad ile). Sabit (kodda): 4 / talep, 5 MB, 30 kayıt / saat / kullanıcı, kenar 12.000 / 40 milyon piksel; depolama kökü belgelerle ortak `DOCUMENTS_DIR` (`DOCUMENTS_MIN_FREE_BYTES` boş disk koruması aynen uygulanır). Audit eylemleri: `work_item.created|status_changed|assigned|updated|commented|cancelled|attachment_added|attachment_removed` (başlık/açıklama/yorum metni/dosya adı yazılmaz).
